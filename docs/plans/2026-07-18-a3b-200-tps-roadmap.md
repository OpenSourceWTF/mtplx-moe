# A3B 200 TPS Performance Roadmap

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> `superpowers-optimized:subagent-driven-development` (recommended) or
> `superpowers-optimized:executing-plans` to execute this plan task-by-task.
> Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Raise the local PR-174 A3B beneficial stack from 153.044 tok/s to at
least 200 tok/s on the upstream `long_code_uncapped` natural-stop K1/TGY4
contract without weakening correctness, engagement, or benchmark gates.

**Architecture:** Remove measured end-to-end cycle latency in isolated,
construction-installed units. Start with captured-primary M1 rejection repair,
reprofile the resulting stack outside the measured path, and pursue target-logit
or packed full-attention Q/K/V work only when the new profile proves sufficient
headroom. Promote only independently positive changes, then measure their joint
stack before running the wider K/prefill matrix.

**Tech Stack:** Python 3.12, MLX, `mx.compile`, fixed-shape Metal kernels,
pytest, Ruff, the process-isolated A3B harness, and out-of-band Metal profiling.

**Assumptions:**

- Assumes local beneficial-stack commit `960849b0a76181338b82ced875e237ee18ee3770`
  remains the unchanged control. This plan does not include rejected projection,
  draft-summary, or MTP-phase experiments.
- Assumes the target metric is natural-stop K1/TGY4 throughput. Fixed 1024/1024
  and TGY8 results are excluded and cannot establish the verdict.
- Assumes arithmetic, sampling order, engagement, output SHA where arithmetic is
  unchanged, acceptance, tokens/cycle, zero compiled fallback, and zero growth
  demotion remain correctness gates. RNG compensation is excluded.
- Assumes exact model and request facts are validated once at construction or
  installation. No hot-path environment reads, validation, eligibility checks,
  fallback accounting, silent stock fallback, or proof counters may be added.
- Assumes every candidate is developed and benchmarked in its own worktree. A
  wash or regression remains isolated and is not stacked without a later,
  bottleneck-shifted remeasurement.

## Latency budget

The beneficial-stack measurement is:

| Metric | Value |
|---|---:|
| Throughput | 153.044181 tok/s |
| Cycle time | 10.822248 ms/cycle |
| Derived tokens/cycle | 1.656282 |
| Cycle time required for 200 tok/s | 8.281410 ms/cycle |
| Required reduction | 2.540838 ms/cycle |

The captured-repair trace observed 282 rejections over 1,595 cycles and
10.698209 ms per existing M2 repair. Its measured region is therefore
1.891470 ms/cycle. At unchanged tokens/cycle, deleting that entire region at
zero replacement cost would yield 185.458 tok/s, not 191.37 tok/s. If 191.37
came from another baseline, it must be labeled with that baseline and must not
be used for this plan.

The real remaining budget after installing an M1 repair of latency `L` ms is:

```text
remaining_ms_per_cycle = 2.540838 - (282 / 1595) * (10.698209 - L)
                       = 0.649368 + 0.176803 * L
```

Examples:

| M1 repair latency | Repair saving | Residual saving needed |
|---:|---:|---:|
| 0 ms | 1.891470 ms/cycle | 0.649368 ms/cycle |
| 2 ms | 1.537864 ms/cycle | 1.002974 ms/cycle |
| 4 ms | 1.184258 ms/cycle | 1.356580 ms/cycle |
| 6 ms | 0.830652 ms/cycle | 1.710186 ms/cycle |
